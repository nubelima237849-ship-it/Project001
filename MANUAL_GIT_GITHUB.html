1Cómo viaja tu código

Tu PC guarda una copia del proyecto y GitHub guarda la copia central. Cada cambio sigue este camino:

Idea clave: main es tu versión estable. No trabajes directamente en ella: crea una rama por cada cambio.

2Crear la carpeta de trabajo

  1. Abre la terminal (CMD, PowerShell o Git Bash en Windows).
  2. Cambia al disco donde quieres trabajar y crea la carpeta: 
    # En Windows, cambiar de disco es escribir la letra
D:

# Crear la carpeta contenedora y entrar en ella
mkdir mis-proyectos
cd mis-proyectos
  3. Espacios en nombres: la terminal usa el espacio para separar palabras. Si tu carpeta se llama Mi Carpeta, protégela con escape o comillas. El Tab lo hace solo: 
    cd Mi\ Carpeta
cd "Mi Carpeta"
Consejo: usa guiones en los nombres (mi-carpeta) y evitarás este problema.

3Crear el proyecto Vite + React

Necesitas Node.js 20.19 o superior (o 22.12 o superior). Comprueba tu versión con node -v.

# Crear el proyecto con la plantilla oficial de React
npm create vite@latest mi-app -- --template react

# Entrar, instalar dependencias y probar
cd mi-app
npm install
npm run dev

Abre la dirección que muestra la terminal (normalmente http://localhost:5173). Para detenerlo, pulsa Ctrl + C.

4Iniciar sesión (solo la primera vez)

  1. Guarda tu nombre y correo para los commits. Se hace una sola vez en tu PC: 
    git config --global user.name "Tu Nombre"
git config --global user.email "tu-email@ejemplo.com"
  2. Inicia sesión en GitHub con la herramienta oficial gh: 
    gh auth login
    Elige GitHub.com, luego HTTPS y Login with a web browser. Copia el código que aparece, pégalo en el navegador y autoriza.
  3. Verifica que quedó activo: 
    gh auth status

5Subir la primera versión (main)

  1. Dentro de la carpeta del proyecto, inicia Git y nombra la rama principal main: 
    git init
git branch -M main
  2. Guarda todos los archivos como primera versión (commit): 
    git add .
git commit -m "primer commit: proyecto Vite React inicial"
  3. Crea el repositorio en GitHub y sube main en un solo paso: 
    gh repo create mi-app --public --source=. --push
    Usa --private si quieres que sea privado. Al terminar, tu proyecto aparece en GitHub con la rama main.
Antes de subir, revisa que no haya contraseñas ni claves en tus archivos. El archivo .env debe estar en .gitignore; Vite ya lo incluye en las plantillas nuevas.

6Manejar versiones al modificar

Hay dos herramientas que se complementan:

HerramientaPara qué sirveEjemplo
Rama (branch)Trabajo en curso, una por cada cambioagregar-navbar
Etiqueta (tag)Versión oficial, con número fijov1.0.0

El número de versión sigue el formato MAJOR.MENOR.PARCHE: MAJOR cuando rompes compatibilidad, MENOR cuando añades funciones, PARCHE cuando corriges errores.

# 1. Actualizar main y crear la rama de tu cambio
git switch main
git pull
git switch -c agregar-navbar

# 2. Modifica archivos en tu editor y revisa qué cambió
git status
git diff

# 3. Guardar la versión (commit)
git add .
git commit -m "agrega barra de navegación"

# 4. Subir la rama y abrir el pull request
git push origin agregar-navbar
gh pr create --base main --head agregar-navbar --title "Agrega navbar"

# 5. Cuando esté aprobado: fusionar y actualizar main en tu PC
gh pr merge
git switch main
git pull

Marcar una versión oficial

# Crear la etiqueta sobre main y subirla a GitHub
git switch main
git pull
git tag -a v1.0.0 -m "Primera versión estable"
git push origin v1.0.0

Los tags no se suben con un git push normal: necesitas el comando de arriba o git push --tags.

7Observar y cargar versiones

# Historial de versiones (commits), en una línea cada uno
git log --oneline

# Ramas locales y remotas
git branch -a

# Etiquetas de versión
git tag

# Traer las ramas nuevas de GitHub sin cambiar tus archivos
git fetch origin

# Cambiar a una rama (tus archivos cambian a esa versión)
git switch nombre-de-la-rama

# Ver una versión etiquetada en modo solo lectura
git checkout v1.0.0

# Volver al presente
git switch main
En GitHub web: la pestaña Commits muestra el historial y Tags o Releases muestra las versiones etiquetadas.
git checkout v1.0.0 deja el proyecto en modo "solo lectura". Si haces cambios allí, pueden perderse al cambiar de rama. Para trabajar sobre una versión antigua, crea una rama: git switch -c arreglo-v1 v1.0.0.

8Borrar archivos y carpetas

  1. Borrar del proyecto y de Git: 
    # Un archivo
git rm archivo.txt

# Una carpeta completa
git rm -r nombre-carpeta

# Guardar el borrado como versión y subirlo
git commit -m "elimina archivos innecesarios"
git push
    El borrado también queda registrado en el historial, pero deja de estar en la versión actual.
  2. Dejar de rastrear sin borrar de tu PC (útil para .env o archivos locales): 
    git rm --cached archivo.txt
git rm -r --cached nombre-carpeta
    Después agrégalo a .gitignore, haz commit y push.

9Borrar versiones

9.1 · Borrar ramas que ya no necesitas

# Borrar la rama local (Git avisa si no está fusionada)
git branch -d agregar-navbar

# Borrar la misma rama en GitHub
git push origin --delete agregar-navbar

# Forzar el borrado local SIN fusionar (pierdes ese trabajo)
git branch -D agregar-navbar
Borrar una rama ya fusionada no pierde nada: sus cambios ya están en main.

9.2 · Borrar tags

git tag -d v0.9.0
git push origin --delete v0.9.0

9.3 · Deshacer un commit que aún no subiste

# Quitar el commit y conservar tus cambios en los archivos
git reset --soft HEAD~1

# Quitar el commit y DESCARTAR sus cambios (peligroso)
git reset --hard HEAD~1

9.4 · Deshacer un commit que ya subiste

# Crea un commit nuevo que revierte el anterior (seguro)
git revert id-del-commit
git push

9.5 · Dejar solo las versiones que quieres

Reescribir el historial cambia los commits. Hazlo solo en ramas tuyas que nadie más use. Nunca lo hagas en main compartida sin coordinarlo.
# Unir varios commits recientes en uno (interactivo)
git rebase -i HEAD~3
# En el editor, cambia "pick" por "squash" en los commits a unir

# Si la rama ya estaba en GitHub, actualízala así
git push --force-with-lease

La forma más segura de quedarte solo con lo que quieres:

  1. Fusiona a main con un pull request solo lo que quieres conservar.
  2. Borra las ramas sobrantes, locales y remotas (9.1).
  3. Borra los tags que no quieres (9.2).

Agentes con OpenCode

OpenCode es libre y ya incluye agentes. No necesitas un framework externo para tareas de código. Pasos:

  1. Conecta tus proveedores dentro de OpenCode con /connect (Claude, Gemini u OpenAI, según tengas cuenta o clave).
  2. Mira los modelos disponibles con /models y copia el nombre exacto del que quieras usar.
  3. Crea un agente por archivo en .opencode/agents/: 
    # .opencode/agents/revisor.md
---
description: Revisa cambios buscando errores y regresiones
mode: subagent
model: proveedor/modelo
---
Revisa los cambios actuales. Lista los hallazgos ordenados por
severidad, con archivo y línea. No modifiques código.
    Cambia proveedor/modelo por un nombre que aparezca en /models.
  4. Opcional: define un modelo por defecto del proyecto en opencode.jsonc: 
    {
  "$schema": "https://opencode.ai/config.json",
  "model": "proveedor/modelo"
}
Frameworks como LangGraph o CrewAI sirven para orquestar varios agentes con memoria y pipelines. Son de código abierto y también soportan Claude, Gemini y OpenAI. Empieza con OpenCode y pasa a ellos solo si lo necesitas.
